**Scope:** entire repository — `apps/web` (Next.js 16 frontend), `apps/api` (FastAPI backend), `supabase/` (migrations, config, RLS policies), `Project_Docs/Legal/`, deployment infrastructure (Vercel + AWS EC2), dependencies, tests, and documentation.

# Executive Summary

### Overall Grade: **C-**

This needs to be read as two separate grades, because they diverge sharply:

- **Engineering craftsmanship: B+.** For a solo-founder MVP, the codebase is unusually disciplined — real RLS-enforced multi-tenancy, correctly-implemented AES-256-GCM encryption, a clean dependency-free architecture (no ORM, no component library, no premature abstraction), genuinely accurate FK indexing, zero dead code/TODOs (independently re-verified, not assumed), and legal/technical documentation that is candid about its own trade-offs rather than hiding them.
- **Production readiness for paying, regulated financial-services customers: D+.** A small number of severe, concentrated gaps — one of them a live, currently-exploitable critical security hole — block real production use today. These are fixable in days to weeks, not a rewrite, but they are real and currently open.

### Production Readiness: **~35%**

The product *works* — pipeline runs, extraction, validation, review, and export all function as designed (verified in this session and by the codebase's own end-to-end testing history). What's missing is the operational and security hardening a regulated-industry SaaS needs before it can respons­ibly hold a paying customer's compliance evidence.

### Top Risks (ranked)

1. **The entire FastAPI backend is unauthenticated and publicly reachable** — anyone with a workspace/document UUID can download decrypted customer data or trigger billed LLM calls, no login required.
2. **No soft-delete anywhere** — a single click by any workspace admin permanently destroys the evidentiary record this product exists to preserve, with no undo and no documented backup/recovery story.
3. **Zero automated test coverage of the actual product** — the entire upload→OCR→extract→validate→review→export pipeline, every HTTP route except `/health`, and 100% of the frontend have no tests. Nothing stops a regression from shipping.
4. **No CI/CD at all** — no `.github/workflows`, no pre-merge gate; a broken change can reach production with zero automated check.
5. **The landing page directly contradicts the company's own Privacy Policy** — "no data leaves the EU" (marketing) vs. explicit disclosure that OpenAI and Vercel are not EU-pinned (legal docs, same deploy).
6. **PyMuPDF (`fitz`) is AGPL/commercial dual-licensed** and is used in the proprietary backend with no evidence a commercial license was purchased or the licensing question was even considered.
7. Staging and production share one EC2 process and one Supabase project — a bug or attack against either affects both.
8. No rate limiting anywhere — an LLM-billed endpoint has no cost-abuse protection.

### Critical Blockers (must fix before any paying customer)

- Unauthenticated backend (Security S1)
- No soft-delete on evidence data (Database D1)
- PyMuPDF licensing resolution (Dependency)
- Landing page vs. Privacy Policy contradiction (Legal)

### Quick Wins (cheap, high value, do this week)

- Shared-secret header between Next.js and FastAPI (same-day patch for the critical blocker)
- Fix duplicated page titles (`Privacy Policy — EvidenceOS · EvidenceOS`)
- Remove "No reset flow yet" from production login copy
- Add a confirmation dialog before document/branch deletion
- Fix `--fg-3` contrast (fails WCAG AA across the entire app)
- Replace the keyboard-bypassable "Finish & export" anchor with a real disabled button
- Add `slowapi` rate limiting to the FastAPI pipeline routes
- Prune the unused `anthropic` dependency

### Estimated Technical Debt: **Moderate, concentrated, not diffuse**

Most of the codebase carries very little debt — the debt that exists is heavily concentrated in three places: (1) zero test harness for anything DB/HTTP-touching, (2) no CI/CD, (3) the auth-boundary/environment-separation architecture. Estimated effort: **2-4 weeks** (one engineer) to close every Critical/High item; **4-6 additional weeks** for Medium items (test harness, pagination, monitoring depth, rate limiting).

### Estimated Security Risk: **HIGH** (today), **MEDIUM** (once S1 is patched)

Dominated entirely by the unauthenticated backend. Once that's closed, remaining risk is ordinary SaaS-maturity gaps (password policy enforcement, account enumeration, key rotation, rate limiting) — real, but not urgent-critical.

# 2. Backend Audit

### B1/S1 — Critical: every FastAPI route is unauthenticated (full detail under Security Audit below)

### B2 — High: `async def` route handlers block the shared event loop on synchronous I/O
`apps/api/app/pipeline/router.py` declares all three routes `async def`, but each calls synchronous Supabase/zip-building code directly in the coroutine body instead of offloading it:

```python
# router.py:46-58 (trigger)
resp = (
    client.table("pipeline_runs").select("id, status").eq("id", run_id).single().execute()
)
# router.py:122-131 (export) — build_export_zip does multiple sequential
# synchronous Supabase calls + in-memory zip compression, all on the event loop
zip_bytes = build_export_zip(workspace_id)
```
Since uvicorn runs as a single systemd process with no `--workers` flag, serving **both staging and production simultaneously** (per the ops runbook), one slow export or revalidate call stalls every other request on the box — including the `/health` endpoint UptimeRobot polls. **Fix:** `await anyio.to_thread.run_sync(...)` around every blocking call, or use an async Supabase client throughout.

### B3 — Medium: TOCTOU race on pipeline-trigger status transition
`router.py:61-80` reads `status`, checks it in Python, then schedules the background task — not an atomic `UPDATE ... WHERE status='queued'`. Two concurrent trigger calls for the same run can both pass the check and both schedule `run_ocr_for_pipeline`, which itself does unguarded delete-then-insert (B5) — risking interleaved/duplicated OpenAI-billed extraction work. **Fix:** atomic `UPDATE ... WHERE status='queued' RETURNING id`, check the returned row before scheduling.

### B4 — Medium: no crash/restart recovery for in-flight background pipeline runs
`run_ocr_for_pipeline` (`ocr_worker.py:38-263`) is a fire-and-forget `BackgroundTask`. A systemd restart (a deploy, an OOM kill on the free-tier box) mid-run leaves `pipeline_runs.status` and per-document stage columns stuck at `'running'` forever — no heartbeat, no lease, no reaper. The stuck `'running'` state also blocks the 409 retry guard (B3), so recovery requires a human manually editing the DB row. **Fix:** either a durable `SELECT ... FOR UPDATE SKIP LOCKED` queue, or a stale-run reaper timer.

### B5 — Medium: delete-then-insert without a transaction
`ocr_worker.py:183-187` and `revalidate.py:117-121` both delete then insert `extraction_results`/`validation_results` as two separate HTTP calls to PostgREST, not one transaction. A crash between the two calls leaves a document showing zero extracted fields until manually re-run. `revalidate.py`'s docstring acknowledges this trade-off explicitly; `ocr_worker.py`'s identical pattern (which runs far more often) does not. **Fix:** wrap in a Postgres function callable in one round trip, or use conditional upsert.

### B6 — Medium: no file-parsing safety limits in OCR/extraction
`extractor.py` loads entire files into `fitz`/`docx`/`openpyxl` with no page/row/cell cap and no timeout. Within the 50MB Storage bucket limit, a pathological XLSX/PDF can still consume disproportionate CPU/memory on the single shared process. **Fix:** hard row/page ceilings before iterating, wall-clock timeout on extraction calls.

### B7 — Low: no timeout on the OpenAI extraction call
`field_extractor.py:590-611` sets `temperature=0`/`max_tokens=4096` but no `timeout=`. A hung OpenAI response holds a thread-pool slot indefinitely.

### B8 — Medium: application-layer encryption has sound crypto, weak key management
`app/core/encryption.py`'s AES-256-GCM implementation is cryptographically correct (proper nonce, authenticated encryption, versioned envelope). But: one static key protects every tenant, shared between two independently-managed deployment platforms (EC2 systemd env file + Vercel env store), with no rotation mechanism — the `enc:v1:` version prefix exists but nothing branches on it, so rotating the key today would make every existing row permanently undecryptable without a full re-encryption pass first. Disclosed candidly in the code's own docstring and in customer-facing legal docs (see Legal Audit) — a real production risk nonetheless, not a hidden one.

### B9 — Unverified: dependency CVEs
Cannot check live CVE databases from this environment. Recorded versions (`fastapi==0.139.0`, `starlette==1.3.1`, `cryptography==49.0.0`, `pydantic==2.13.4`, `httpx==0.28.1`, `PyJWT==2.13.0`, `uvicorn==0.51.0`, `openai==2.45.0`, `anthropic==0.116.0`, `pymupdf==1.28.0`, `python-docx==1.2.0`, `openpyxl==3.1.5`, `supabase==2.31.0`) should be run through `pip-audit`/`safety check` in CI before customer onboarding.

# 3. Frontend Audit

**Server/Client boundaries are disciplined and correct.** Auth pages are pure Server Components with zero client JS for the happy path (`(auth)/login/page.tsx`, `signup/page.tsx`). Every list/detail dashboard page is a Server Component; only genuinely-interactive leaves (`upload-zone.tsx`, `field-review-card.tsx`, `sidebar-shell.tsx`, `entity-profile-form.tsx`, `keyboard-shortcuts.tsx`) are `"use client"`. Dependency footprint is minimal (`next`, `react`, `react-dom`, `@supabase/ssr`, `@supabase/supabase-js` — nothing else in production deps), so there's no bundle-bloat concern.

### Real bugs found

- **Keyboard-bypassable export gate.** `review/[documentId]/page.tsx:142-150` uses a styled `<Link>` with `aria-disabled` + `pointer-events-none` to "disable" the Finish & Export CTA when review is incomplete. `pointer-events-none` blocks clicks; it does **not** stop keyboard Enter on a native `<a>`. A keyboard-only reviewer can Tab to it and press Enter to navigate to `/export` regardless of review completeness (the export page independently re-gates, so no data leaks — but the review page's own UI gate is a lie for keyboard users). **Fix:** a real `<button disabled>`.
- **No confirmation before destructive actions.** `documents/delete-document-button.tsx:18-22` calls `deleteDocument()` directly from `onClick` — no `confirm()`, no modal, no undo — and cascades to every version/extraction/validation of that document (see also Database D1). `entity-profile-form.tsx:245-252`'s `removeBranch` has the identical gap.
- **Zero route-level loading/error states.** Confirmed via glob: no `loading.tsx`, `error.tsx`, or `not-found.tsx` exists anywhere in `app/`. Every workspace page does 1-3 sequential/nested Supabase queries with no `<Suspense>` boundary — blank screen until everything resolves, and any unexpected Server Component error surfaces Next.js's generic unstyled error page.
- **Pipeline progress has no live-update mechanism.** `start-run-form.tsx` calls `router.refresh()` exactly once, immediately after creating the run (while still `'queued'`). Nothing polls, subscribes to Supabase Realtime, or auto-refreshes while a run is `'running'` — the UI was built to *look* live (status dots, "running" highlight styling) but requires a manual page reload to actually update.
- **Field review has no optimistic UI, full-page cost per click.** `review/actions.ts`'s `submitFieldReview` is awaited end-to-end (DB upsert + synchronous FastAPI `/revalidate` call), then `field-review-card.tsx:93-95` calls `router.refresh()`, re-rendering every field's card, not just the one that changed. For a document with up to 61 fields, reviewed one at a time, this is the single highest-impact frontend performance finding — every approve/reject pays a full round trip with no visual anticipation of the result.

**Positive findings:** no hydration risk found (all date formatting happens server-side, once, in Server Components; the one `crypto.randomUUID()` call is client-only and used for a React key, not rendered content); no raw `<img>` tags anywhere (the app uses no raster images at all, so there's no `next/image` migration debt).

# 6. Security Audit

### S1 — CRITICAL: the entire FastAPI backend is unauthenticated and publicly reachable

**Fully verified, not speculative.** `apps/api/app/pipeline/router.py` has zero auth dependency on any of its three routes (confirmed by grepping the whole tree for `Depends|Authorization|Bearer|api_key` — zero hits outside the OpenAI key). The code's own comment admits this is deliberate: *"Unauthenticated at this layer — the caller (a Next.js Route Handler) verifies workspace membership first"* (`router.py:13-16`), and the Next.js side confirms: *"Every FastAPI pipeline endpoint is unauthenticated at the HTTP layer and trusts its caller's network position, not the request itself"* (`export/download/route.ts:9-14`). Infrastructure confirms this "network position" trust isn't actually a boundary: the EC2 security group opens **port 443 to `0.0.0.0/0`** (`Phase_7_Deployment/01_aws_setup_log.md` §5), and the API is live today at `https://18.196.98.199.sslip.io`.

**Concrete impact:** anyone who obtains a `workspace_id`, `run_id`, or `document_version_id` (UUIDs — leaked via browser history, shared links, error messages, Vercel logs, a support screenshot) can:
- `GET /pipeline/workspaces/{id}/export` and download that workspace's **entire decrypted DORA RoI export** with no login — the endpoint uses a service-role client that bypasses RLS entirely.
- `POST /pipeline/runs/{id}/trigger` to re-run OCR/LLM extraction on someone else's data, burning their OpenAI spend.
- `POST /pipeline/documents/{id}/revalidate` on arbitrary documents.

**Fix, prioritized:** (1) same-day — a shared-secret header the Next.js server includes and FastAPI validates with `secrets.compare_digest`; (2) restrict the EC2 security group to Vercel's published IP ranges; (3) best — move the backend off the public internet entirely (VPC peering / private networking) and verify the caller's forwarded Supabase JWT rather than trusting network position.

### S2 — High: password policy enforced client-side only
`signup/page.tsx:120`/`login/page.tsx:128` set `minLength={8}` (trivially bypassable). The `signup` Server Action performs no server-side length/complexity re-check. `supabase/config.toml:181,184` shows the actual local floor is `minimum_password_length = 6` with no complexity requirement — production Supabase dashboard settings couldn't be verified from this repo, but nothing in the codebase enforces a stronger floor independent of whatever the dashboard says.

### S3 — Medium: account enumeration via raw Supabase error messages
`(auth)/actions.ts:79-81,96-98` pass Supabase's raw `error.message` straight into the redirect URL for both signup and login, unnormalized — risking leaking which of "email already exists" vs. "invalid credentials" occurred, exposing the workspace member list (sensitive B2B info) to enumeration.

### S4 — Medium: shared single environment amplifies every other finding
Staging and production share one EC2 box and one Supabase project. Combined with S1 and B2, a single bad actor or malformed request against either surface can degrade the box or touch the same live customer data serving both.

### S5 — Low: CORS is correctly scoped but provides no real protection given S1
`app/main.py:71-77` uses a concrete origin list, not a wildcard (correct), but since no route requires authentication at all, CORS provides no meaningful protection — a direct `curl` bypasses it entirely.

### S6 — Verified clean: no secrets in tracked source
`.gitignore` correctly wildcards `.env.*`/`*.pem`; only the three `.env.example` templates (clearly fixed local-demo values) are tracked. Good hygiene, worth stating positively.

### S7 (=B8) — Medium: sound encryption, weak key management (see Backend Audit B8)

### Severity summary

# 7. Performance Audit

*(Synthesized from findings across all three audits — no separate live Core Web Vitals measurement was performed in this pass; see caveat below.)*

**Backend:**
- Single-process, single-worker uvicorn handling blocking synchronous I/O inside `async def` routes (B2) — the most severe backend performance finding, since it means one slow request can stall the entire process, including health checks, for both staging and production simultaneously.
- No pagination anywhere (Database/API D-series/A5) — `documents` and `pipeline` list pages fetch every row, every nested join, unbounded, on every page load. This will degrade measurably (not hypothetically) as any real workspace accumulates a few hundred pipeline runs.
- No caching layer of any kind (no Redis, no in-memory cache, no CDN-level caching for dynamic pages) — every dashboard page re-fetches and re-decrypts from scratch on every request.
- No timeout on the OpenAI extraction call (B7) — a slow LLM response can hold a thread-pool slot indefinitely, degrading throughput for queued work.

**Frontend:**
- Field review (`field-review-card.tsx`) does a full synchronous round trip (DB write + FastAPI HTTP call) and a full-page `router.refresh()` for every single field decision, with no optimistic UI — the single highest-impact *frontend* performance/UX finding, given this is the core, most-repeated workflow in the product (up to 61 fields per document).
- No memoization/virtualization found on any list (documents, pipeline runs, extracted fields) — not yet a measured problem given current data volumes, but will become one at the same scale where pagination (above) becomes necessary.
- Bundle size is minimal and healthy — five runtime dependencies total, no component library, no icon kit, no date library. This is a genuine strength, not a risk.
- No images anywhere in the app (verified via grep for `<img>`) — no LCP-image or `next/image` concern exists because there's nothing to optimize.

**Not measured / cannot verify:** actual Core Web Vitals (LCP, CLS, INP, TTFB) were not captured live via Lighthouse/PageSpeed in this audit pass — stating this explicitly rather than guessing a score. Recommend running Lighthouse CI against the production URL before/after the field-review optimistic-UI fix, since that's the interaction most likely to show up in INP measurements.

# 8. Accessibility Audit (WCAG 2.2 AA)

### Contrast failures — computed directly from `globals.css` hex values

- `--fg-3: #9c948c` on `--bg: #faf9f6` → **≈2.84:1**; on `--surface: #ffffff` → **≈2.99:1**. Both fail the 4.5:1 normal-text AA minimum (the second also fails the 3:1 large-text minimum).
- Dark mode `--fg-3: #6f665e` on `--bg: #1a1817` → **≈3.15:1** — clears large-text AA, fails normal-text AA.
- `text-fg-3` is used pervasively for exactly the small dense text where this matters most: table headers, timestamps, field codes, empty-state copy. This is a **systemic** failure, not an isolated one. **Fix:** darken `--fg-3` toward `--fg-2` (which computes at a comfortable 5.46:1), or reserve current `--fg-3` strictly for ≥18px decorative text.
- All other checked pairs (`--fg`/`--fg-2`/`--danger`/`--accent`/`--success` on their backgrounds) pass AA comfortably.

### Color-only information
`field-review-card.tsx`'s review-decision badge (text + icon) is `hidden` below the `sm:` breakpoint, leaving a 3px border color as the **only** signal of approved/rejected/pending on mobile — a genuine WCAG 1.4.1 violation for exactly the kind of quick phone-based spot-check a reviewer might do.

### Keyboard operability
- Field-review buttons, pipeline `<details>/<summary>` rows, and the signup consent checkbox are all correctly keyboard-operable (real `<button>`/native elements).
- Upload drop-zone's `role="button"` div handles Enter but not Space (`upload-zone.tsx:161-176`) — violates WAI-ARIA button conventions; Space instead scrolls the page.
- Mobile sidebar drawer has no keyboard-accessible close mechanism — no Escape handler, no visible close button, only a click-outside handler.

### Labels and hover-only content
- The field-review edit-mode `<input>` (`field-review-card.tsx:119-126`) has no `<label>`/`aria-label` — a screen reader announces an unlabeled textbox.
- The rejection-reason textarea relies on `placeholder` alone for labeling, not `htmlFor`/`aria-labelledby` — explicitly discouraged by WCAG guidance.
- Validation rule explanations (`field-badges.tsx:44-51`) are exposed **only** via the `title` attribute — hover-only, no keyboard-focus equivalent, invisible to touch users. This is arguably the single most important explanatory text on the Review page (why a field failed) and it's inaccessible to keyboard-only and touch-only users entirely.

### Positive findings
`role="alert"`/`role="status"` are used consistently across nearly every form/action in the app — a genuinely good, disciplined pattern. The `sr-only` custom-checkbox pattern in `start-run-form.tsx` is textbook-correct.

### Focus indicators
Every text input across the app uses `outline-none focus:border-accent` — strips the browser default focus ring for a subtler 1px border-color change, materially weaker for low-vision keyboard users. Buttons/links appear to retain the browser default (not stripped).

# 9. DevOps Audit

**No CI/CD exists at all.** Confirmed: no `.github/` directory anywhere. No automated test run, no lint gate, before either Vercel's auto-deploy (frontend, on every push to `claude`/`main`) or the manual `deploy.sh` (backend). A broken `pytest` suite or `ruff` violation can reach production with zero automated check.

**`deploy.sh` gaps beyond what's already documented in `CHALLENGES.md` C1-C10:**
- Syncs the local working tree, not a git checkout — uncommitted changes deploy silently with no record of what shipped (the ops runbook itself flags this as a known, unfixed gap).
- No rollback mechanism — the tar extraction overwrites `/opt/evidenceos-api` in place; there is no previous-version fallback if a subtler bug passes the health check.
- `pip install` has no hash verification/`--no-deps` — a compromised PyPI package could install silently on a redeploy.

**Environment variable drift risk is structural, not just historical.** `DOCUMENT_ENCRYPTION_KEY` must match byte-for-byte across three independently-managed stores (`apps/api/.env`, `/etc/evidenceos/api.env`, Vercel dashboard) with no automated check that they agree — a silent drift here doesn't crash cleanly, it raises `InvalidTag` on every decrypt, which looks like data corruption, not a config issue.

**No backup/disaster-recovery story documented anywhere** for either the Supabase database or the EC2 box — no PITR configuration mentioned, no AMI/snapshot policy, no restore runbook.

**No `Dockerfile` for the backend** — the EC2 deployment depends entirely on the box's own hand-configured Python/systemd/nginx state, none of which is captured as code in this repo. Ironic given local dev now uses Docker for Supabase but the actual backend service has no reproducible build artifact.

# 10. Database Audit

### D1 — High: no soft-delete anywhere; evidence data is permanently destructible
Every foreign key uses `on delete cascade`, and any workspace owner/admin can hard-delete a `documents` row, cascading away every version, extraction, validation, **and the human review sign-off trail** — the core value proposition of an evidence/audit product. No `deleted_at` column exists in any of the 10 migrations, no archive table, no deletion-lock once a document has been included in a filed export. **This is the single highest-priority database finding** given the product's stated purpose.

### D2 — Low: `field_reviews` UPDATE policy's `WITH CHECK` doesn't re-verify role
Currently not exploitable (no column interacts with role today), but a defense-in-depth gap worth closing before extending this table.

### D3 — Low: redundant index
`prd_run_id_idx` on `pipeline_run_documents.pipeline_run_id` duplicates the leading column of the table's own composite primary key — pure write-overhead waste, safe to drop.

### D4/D5 — Confirmed clean, stated positively
RLS helper functions (`is_workspace_member`/`has_workspace_role`) are correctly indexed via the `workspace_members` composite primary key — no full-table-scan risk at scale. `extraction_results.confidence`/`validation_results.status` have correct schema-level CHECK constraints, not just application-level validation.

### D6 — Low: no down-migrations / rollback plan
No migration includes a corresponding rollback script. The `0002→0003→0004` sequence is itself a real example of a fix-forward cycle after a mistake — evidence this already cost real time once.

# 11. API Audit

# 16. Product Audit

Answering as a startup CTO evaluating this for real adoption:

- **Would users trust this product?** Conditionally — the visual design and candid legal disclosure build trust, but the landing-page-vs-privacy-policy contradiction and the "No reset flow yet" admission actively undermine it for anyone who reads closely, which compliance buyers will.
- **Would investors be impressed?** By the engineering discipline and the RLS/encryption architecture, yes. By the complete absence of tests and CI/CD on a regulated-data product, no — this is exactly the kind of gap a technical diligence process surfaces immediately.
- **Would enterprise customers adopt it?** Not in its current state — S1 (unauthenticated backend) and D1 (no soft-delete on evidence) are both disqualifying for a compliance-evidence product, full stop, regardless of how good the rest of the implementation is.
- **Would this pass technical due diligence?** No — the unauthenticated backend and zero test coverage of the critical path would be flagged as blocking issues by any competent technical reviewer within the first hour.
- **Would this survive production traffic?** Not safely — the single-process blocking event loop (B2) and unbounded queries (A5) mean it degrades, not scales, under real concurrent load.
- **Would this pass a SOC2 review?** No — no CI/CD, no documented backup/DR plan, no access logging/monitoring depth beyond basic uptime checks, and an openly-admitted unauthenticated internal API would all be findings.
- **Would this pass a security review?** No, not as-is — S1 alone is disqualifying; a real pen test would find it in minutes.
- **Would this pass an accessibility review?** No — the systemic `--fg-3` contrast failure alone fails WCAG AA; several other findings (mobile-hidden status badges, hover-only validation explanations) compound it.
- **Would this pass a design review?** Largely yes — the visual/UX craftsmanship is the strongest part of this audit; the fixable issues (confirmation dialogs, keyboard gate, contrast) are execution details, not design-direction problems.
